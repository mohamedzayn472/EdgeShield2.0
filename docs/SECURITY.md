# Security and privacy model

## Assets and trust boundaries

Protect user-selected SMS content, trusted detector/runtime artifacts, decision integrity and understandable output. The SMS and all Llama output are hostile inputs. The operating-system account, installed Python packages and provisioned runner are trusted dependencies; this application does not defend against a fully compromised host.

The strongest application boundary is raw text to structured evidence. Only enumerated IDs and bounded numeric/enum values may reach the prompt. A keyword-based prompt-injection filter alone would not be an adequate boundary.

## Threats, controls and verification

- **Prompt injection:** reject arbitrary evidence fields and never interpolate SMS content into the prompt. Exercise at least ten attacks containing instruction overrides, role delimiters, fake JSON, HTML, encoded text and requests to disclose secrets. Assert absence of attack strings in the captured backend prompt.
- **Hallucination and unsafe advice:** accept only approved evidence-supported explanations; otherwise use a deterministic template. Always generate `DO:` in application code. Test invented domains, phone numbers, certainty, unsupported cues and imperatives.
- **False positive/negative decisions:** use validation-selected abstention thresholds; publish per-source metrics and failure examples from public/synthetic data. Do not call low-risk messages authenticated or promise protection.
- **Sensitive-data leakage:** no inbox access, no raw-message persistence and no model prompt excerpts. Inspect normal and failure output with a unique synthetic sentinel. Avoid debugging logs containing subprocess prompts or exception payloads.
- **Terminal escape injection:** normalize/reject controls and do not echo untrusted model output. Test ESC, bidi formatting, combining characters and oversized Unicode input.
- **Resource exhaustion:** cap input, evidence size, generated bytes and runtime duration. Kill and reap the runtime on timeout. Check malformed artifacts before allocation where practical. The OS can still experience memory pressure during genuine model loading; measure on Pi.
- **Artifact tampering:** verify expected SHA-256 hashes before use and reject missing/mismatched model/runtime/tokenizer files. A hash obtained from an attacker-controlled manifest is not authenticity. Acquire artifacts from trusted sources and protect the manifest.
- **Command injection:** use an argument list with `shell=False`; no SMS text in filenames or commands. A runtime configuration is trusted local configuration, not an importable user message.
- **Network dependency:** application inference has no cloud provider. Validate by disabling connectivity and tracing attempted networking separately. Static inspection alone cannot prove behavior of compiled dependencies.
- **Unauthorized local access:** use a trusted account and file permissions. This prototype does not encrypt RAM, swap or terminal scrollback and cannot erase copies created by the OS.

## Residual limitations

Indicators are noisy and may be evaded through obfuscation or unfamiliar language. A phrase allowlist constrains what the model can say; it does not prove the classifier is right. An accepted explanation means its wording passed application rules, not that a malicious sender was identified. Even a tested validator cannot guarantee perfect hallucination prevention.

Artifacts trained on public SMS may include public-corpus vocabulary. Do not fit or redistribute models on private inbox content. Do not publish licensed weights or tokenizer assets merely because the repository is ready for GitHub.

## Safe incident handling

If inference fails, show the detector outcome, deterministic advice and an explicit fallback reason code. Retain only approved status/timing fields. Do not include SMS text in issue reports. Reproduce bugs with fictional messages and reserved domains. A corrupted detector should fail clearly rather than silently produce a placeholder score.
